# Customer Transaction Import — Design

## Intent

A production-style Spring Boot + Spring Batch service that imports a CSV of ~1M
customer transactions into Postgres. The point is to handle everything that can
go wrong during a large import the way a real system would: bad rows, crashes
mid-file, re-runs, transient database errors, and operator visibility.

## Goals

- Import 1M rows reliably and reasonably fast (target: well under 2 minutes on a laptop).
- Bad rows never kill the job; each one is recorded with line number, raw content and reason.
- A job that crashes or is stopped resumes from its last committed chunk, not row 1.
- Re-importing the same file never creates duplicate data.
- Transient DB failures are retried; permanent ones fail the job loudly.
- A clear summary per run: read / written / skipped / duplicates, and status.

## Non-goals

- Fraud scoring, enrichment from external services, multi-file orchestration.
- Horizontal scale-out (remote partitioning / multiple app instances).
- A UI.

## Anti-goals (would be a failure even if it "works")

- Silently dropping rows: every input line is accounted for as written or rejected.
- Partial chunks committed (data in the target table without the matching batch metadata).
- Duplicate transactions after a restart or a re-run.

## Record shape (decided)

CSV with header:
`transaction_id,customer_id,amount,currency,type,timestamp,merchant,status`

Generated by a script with a realistic share (~1%) of bad rows: missing fields,
non-numeric / negative amounts, bad dates, unknown currencies, invalid enum
values, wrong column count, duplicate transaction IDs.

"Processing" (decided) = validate, clean (trim, upper-case codes), convert to
proper types, save. Nothing heavier.

## Stack (my call)

Java 25, Maven, Spring Boot 4.1.2 (Spring Batch 6), Postgres 17 in Docker
Compose, Flyway for all schema (app + Spring Batch metadata), Testcontainers for
integration tests.

## How it works (my calls)

- **Trigger:** `POST /api/imports {"file": "<path>"}` returns `202` with the job
  execution id; the job runs on a background executor. `GET /api/imports/{id}`
  reports status and counts. `POST /api/imports/{id}/restart` and
  `POST /api/imports/{id}/stop` for operators.
- **Job identity / idempotency:** identifying job parameters are the file's
  absolute path and its SHA-256. Re-submitting a file that already completed is
  rejected (409). Same name with new content is a new import. Belt-and-braces:
  `transaction_id` is a primary key and inserts use `ON CONFLICT DO NOTHING`;
  conflicting rows are recorded as `DUPLICATE` rejections, not lost.
- **Pre-flight checks:** file exists, readable, non-empty, header matches
  exactly. Failing any of these fails the job immediately (no point skipping 1M rows).
- **Step:** single-threaded chunk step, chunk size 1000 (configurable), reading
  all columns as strings, then a processor that validates and converts.
  Single-threaded is deliberate: `FlatFileItemReader` is only restartable when
  used by one thread. Partitioning is documented as the next step if needed.
- **Skips:** parse errors and validation errors are skippable and recorded in
  `rejected_transaction` from a skip listener (same transaction as the chunk).
  Skip limit is configurable (default 50,000); beyond it the job fails, because
  a file that bad is probably wrong as a whole.
- **Retries (revised during build):** no in-step retry. Spring Batch 6 retries a write inside
  the same transaction, which cannot work on Postgres (the transaction is aborted after an
  error). Instead a run that fails on a transient error (connection, deadlock, serialization,
  server shutdown) is restarted automatically from its last checkpoint with exponential backoff,
  up to 3 times. Runs that end `UNKNOWN` (rollback failed with the connection) are treated the
  same way, which is safe because data, rejections and checkpoint share one transaction.
- **Crash recovery:** on startup, executions left `STARTED` by a crashed process are marked
  `FAILED` so they can be restarted. Assumes a single app instance.
- **Graceful shutdown / stop (revised during build):** a stop sets the job execution to
  `STOPPING`; the step ends `STOPPED` at its next commit. `JobOperator.stop()` is not used: it
  writes a stale step execution context that can move the restart position backwards.
- **Observability:** progress log every N chunks, end-of-job summary log,
  Actuator health/metrics (Spring Batch Micrometer metrics included).

## Left to the builder

Exact validation bounds, log format, API error body format, connection pool size.
